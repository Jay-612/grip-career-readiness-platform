2. Round-by-Round Detailed Rubric

Live Coding Problem Statement Target Latency: < 5ms

"Design an in-memory distributed rate limiter with sliding window log algorithm capable of handling 50,000 RPS per cluster node."

Evaluate candidates on race-condition avoidance (Mutex vs Redis ZREMRANGEBYSCORE pipeline), thread-safety, and memory leaks from inactive user keys.

Redis Sliding Window Implementation (Go / Java Idiom) SlidingWindowRateLimiter.java 
public class SlidingWindowLimiter {
    private final JedisPool jedisPool;
    private final int maxRequests = 100;
    private final long windowSizeMs = 60_000L;

    public boolean allowRequest(String userId) {
        long now = System.currentTimeMillis();
        String key = "rate:" + userId;

        try (Jedis jedis = jedisPool.getResource()) {
            Transaction pipe = jedis.multi();
            // 1. Remove old timestamps falling outside the sliding window
            pipe.zremrangeByScore(key, 0, now - windowSizeMs);
            // 2. Push current request timestamp with a unique UUID member
            pipe.zadd(key, now, UUID.randomUUID().toString());
            // 3. Fetch count of active elements in current window
            Response<Long> count = pipe.zcard(key);
            // 4. Auto-expire key after window to prevent Redis memory leak
            pipe.expire(key, (int)(windowSizeMs / 1000) * 2);
            pipe.exec();

            return count.get() <= maxRequests;
        }
    }
}
warning

Common Student Pitfalls & Elimination Factor

Most candidates forget cleanup routines for inactive user keys, causing memory exhaustion in Redis over 48 hours. Proactively mentioning background key evictions, setting a Redis TTL EXPIRE, or comparing sliding window log vs sliding window counter will immediately set your answer apart.
